# 无损转录优化设计

日期：2026-07-22

状态：待用户审阅

适用范围：`backend/transcriber.py`、`backend/main.py`、`backend/summarizer.py` 及相关测试

## 1. 背景

当前流水线把 ASR 生成的 Markdown 字符串直接交给 LLM 做自由文本改写，再以字符长度比例判断是否丢失内容。真实任务 `2f0c1c44` 中，原始 ASR 正文约 8 万字符，优化稿丢失约 3.1 万字符。复核表明多个 LLM 块很可能返回空内容；现有块级和全文级兜底都要求输出先为非空，因此空输出反而绕过兜底并在合并阶段被静默跳过。

此外，当前转录器输出英文元信息，而优化器只清理部分中文元信息，导致 `Detected Language`、`Language Probability` 和正文标题进入 LLM 输入。无标点 ASR 文本也会让句子切分退化为机械硬切。

用户选择严格无损模式：允许修正错别字、专有名词、标点和分段，但禁止删除任何口语、重复、寒暄、引用、举例或其他已转录内容。无法证明安全的修改必须回退原文。

## 2. 第一性原理与系统不变量

原始 ASR 文本是唯一事实源，LLM 只是一个不受信任的修改建议生成器。最终稿只能由程序根据原始文本和通过验证的修改确定性构造。

系统必须始终满足以下不变量：

1. 原始正文不可变，并始终单独保存。
2. 原始正文中的每个字符区间恰好归属于一个源段，不得出现空洞或重叠归属。
3. 每个源段都有稳定 ID、原始起止偏移和原文哈希。
4. LLM 的响应契约禁止创建、删除、重复或重排源段 ID；程序不信任响应顺序，只按 ID 映射结果。
5. LLM 返回空内容、格式错误、截断、漏 ID、重复 ID 或过度改写时，不合格内容不得进入最终稿。
6. 单段缺失、重复、为空或内容校验失败时只回退该段；整个响应不可解析或被截断时才回退或重试整个批次。
7. 最终稿严格按原始 ID 顺序拼接，不依赖模糊重叠去重。
8. Markdown、标题和语言元信息只能在存储或展示边界生成，不得作为正文送入 LLM。

## 3. 方案比较

### 3.1 现有自由改写加兜底

保留 4000 字符自由改写，只修复空输出并增加对齐验证。改动小，但一整个大块仍是单一失败域，验证只能事后推断内容是否安全。

### 3.2 带 ID 的分段守恒（采用）

先把正文确定性切成小源段，为每段分配稳定 ID；一次请求携带多个连续源段，LLM 必须按相同 ID 返回修正版。程序逐段验证并逐段选择优化文本或原文。该方案能结构性证明“没有漏段”，实现成本适中。

### 3.3 编辑补丁模式

让 LLM 只返回字符位置补丁，再由程序应用。理论约束最强，但模型生成偏移位置容易出错，中文标点插入也会造成后续偏移漂移，第一版不采用。

## 4. 目标架构

### 4.1 结构化转录载荷

内部流水线不再把 Markdown 当作业务数据。统一使用结构化载荷：

```text
TranscriptPayload
  body: 原始纯正文
  detected_language: 规范化语言代码或 None
  source_segments: 可选的 ASR/VAD 原始段
  title/source_ref: 展示元信息
```

转录器或字幕解析器产生 `TranscriptPayload`；文件保存时才渲染为 Markdown。为了控制改动范围，可以保留现有 Markdown API 兼容层，但 optimize 主路径必须接收纯正文。

### 4.2 确定性源段

当 ASR 已提供可靠句段或 VAD 段时优先使用这些边界；否则使用确定性字符切分：

- 目标源段长度：300 字符。
- 可接受范围：200–450 字符。
- 在目标位置附近优先选择段落、句末标点、句中标点或空格边界。
- 找不到边界时按字符位置硬切，但禁止切断连续 ASCII 单词、URL 或数字串。
- 所有段的 `[start, end)` 必须连续覆盖完整正文，既无空洞也无重叠。
- ID 由序号和原始偏移生成，例如 `seg-000123-036900-037200`。

源段本身不重叠。边界理解问题通过请求上下文解决，而不是通过重复生成正文解决。

### 4.3 请求批次与只读上下文

连续源段组成一个请求批次：

- 每批可编辑正文目标约 2400–3000 字符。
- 每批附带前后各最多 200 字符只读上下文。
- 上下文明确标记为 `editable: false`，没有可输出 ID。
- LLM 只允许返回批次内可编辑段的结果。
- 批次之间可以串行处理，第一版质量优先，不引入 optimize 并发。

请求示例：

```json
{
  "left_context": "只读上文……",
  "segments": [
    {"id": "seg-000001-000000-000300", "text": "hello 大家好……"},
    {"id": "seg-000002-000300-000612", "text": "今天我们的嘉宾……"}
  ],
  "right_context": "只读下文……"
}
```

期望响应：

```json
{
  "segments": [
    {"id": "seg-000001-000000-000300", "text": "Hello，大家好……"},
    {"id": "seg-000002-000300-000612", "text": "今天我们的嘉宾……"}
  ]
}
```

如果模型或兼容 API 支持 JSON Schema，可使用结构化响应；否则按普通 JSON 解析，但执行相同验证，不因供应商能力降低安全标准。

## 5. 两层验证

### 5.1 结构验证

每个批次必须满足：

- HTTP/API 调用成功。
- 至少存在一个 choice，消息内容非空。
- `finish_reason` 表示正常结束；截断、内容过滤或未知结束原因不得直接采用。
- 响应可解析为预期 JSON 对象。
- 响应中的 ID 必须能映射到当前批次；未知 ID 被忽略并记录异常。
- 每个预期 ID 最多采用一次；缺失、重复或 `text` 为空的 ID 单独回退原文。
- 响应数组顺序不作为组装顺序，程序始终恢复原始 ID 顺序。

结构验证失败时：

- API 瞬时错误或 JSON 格式错误允许重试一次；重试仍失败则该批次全部使用原文。
- 因输出长度截断时，把批次对半拆分后各重试一次。
- 已成功解析的响应按 ID 独立验证，单个 ID 的结构错误不牵连其他合格 ID。

### 5.2 内容守恒验证

结构完整只能证明“不漏 ID”，还需防止某个 ID 内部被删改。每段单独执行有序字符对齐：

1. 比较前先忽略空白与标点差异，因为这些是允许修改项。
2. 中文字符、字母和数字的纯删除一律拒绝。
3. 非标点替换只允许作为局部纠错：单个连续替换区最多 12 个原文字符，整段被替换的原文字符不超过 5%。
4. 新增非标点字符总量不得超过原文有效字符的 3%，单次连续新增最多 12 个字符。
5. 不允许换序；对齐结果中的有效字符顺序必须保持。
6. 对有效字符不少于 12 个的源段，开头和结尾各取 12 个有效字符作为锚点；两端都必须至少有 8 个字符按原顺序精确对齐。短于 12 个有效字符的源段只适用前述删除、替换、新增和顺序规则。
7. 任一规则失败，仅该 ID 回退原文。

这些限制允许标点、分段、少量错别字和专有名词修正，但拒绝摘要、润色性重写、整句删除和大段补写。阈值属于安全上限，不以“正常情况下能通过更多文本”为目标。

## 6. 确定性组装

组装器按原始段列表迭代：

1. 读取当前 ID 的验证结果。
2. 验证通过则采用优化文本，否则采用原文。
3. 按 ID 原始顺序拼接。
4. 段之间使用 Markdown 空行；不得再做模糊重叠删除。
5. 最后添加标题和 source 元信息。

组装后执行全文结构校验：

- 输出段数等于源段数。
- 输出采用的 ID 顺序等于源段顺序。
- 每个源段都有 `optimized` 或 `fallback` 状态。
- 任何异常导致整篇回退到由原始源段确定性格式化的版本。

## 7. 可观察性与审计

每次优化记录：

- 任务 ID、模型、批次数和源段数。
- 每批输入/输出字符数、耗时、重试次数和 `finish_reason`。
- 每段状态：`optimized`、`fallback_empty`、`fallback_structure`、`fallback_fidelity`、`fallback_api`。
- 每段原文与结果哈希、原始偏移、替换/新增/删除统计。
- 全文优化采用率和回退率。

日志不得默认记录完整正文。任务目录可生成只含上述元数据的 `optimization_audit_*.json`，用于定位问题而不复制敏感转录内容。

## 8. 语言和元信息处理

- 未知 SenseVoice 标签不得原样视为 ISO 语言代码；仅接受白名单中的已知语言标签。
- 未知标签回退到正文字符检测，无法判断时为 `None`，不得因此自动翻译。
- optimize 接收 `TranscriptPayload.body`，因此不再依赖中英文标题正则来剥离元信息。
- 兼容旧 Markdown 输入时，必须同时识别中英文语言字段、任意级别正文标题和时间戳行，并用单元测试覆盖。

## 9. 失败处理策略

系统采用 fail-closed 策略：

- LLM 不可用：返回完整原文格式化稿。
- 单批失败：失败批次逐段使用原文，其他批次可继续。
- 单段验证失败：只回退该段。
- 全文组装不满足不变量：整篇回退原文格式化稿。
- 审计文件写入失败：记录错误，但不影响正文返回。
- 原始转录保存失败：任务失败，不继续 optimize，因为事实源尚未可靠落盘。

无论何种失败，用户最多失去“优化效果”，不能失去已转录内容。

## 10. 测试设计

### 10.1 单元测试

- 源段覆盖完整正文，无空洞、无重叠、顺序稳定。
- 无标点中文、英文单词、URL、数字串和混合语言边界。
- 空响应、空白响应、无 choice、重复 ID、漏 ID、未知 ID；乱序响应必须按原始 ID 顺序正确组装。
- `finish_reason=length` 时拆批重试；重试失败时回退。
- 纯标点/空白修改通过。
- 少量错别字和专有名词替换通过。
- 删除一个有效字符、删除整句、大段改写、摘要化输出、换序输出失败。
- 单段失败不影响相邻段。
- 全文组装严格保持 ID 数量和顺序。
- 中英文 Markdown 元信息兼容解析。
- 未知语言标签不会触发错误翻译。

### 10.2 故障回归测试

构造 21 个无标点长块，模拟真实故障中的第 1、3、4、12、13、14、16、20 批返回空内容；断言最终正文仍完整包含所有源段，失败段状态均为 fallback。

另外覆盖：

- 输出长度看似达标但删除开头。
- 删除原文同时扩写其他内容，使总长度不变。
- 重复常见口语以欺骗 n-gram 覆盖率。
- 一个批次截断，其他批次正常。
- JSON 包含全部 ID，但其中一个 ID 的正文为空。

### 10.3 真实任务验收

使用任务 `2f0c1c44` 的原始 ASR 产物重新执行 optimize：

- 主持人开场白必须存在。
- 21 个旧块对应的所有源字符范围都有最终去向。
- 不得出现静默空段。
- 审计结果能解释每段采用优化或回退的原因。
- 若模型继续返回异常内容，允许优化采用率下降，但最终正文必须完整。

## 11. 实施边界与顺序

实施分为两个可独立验证的阶段：

1. 安全补丁：修复当前空输出和全文空输出绕过兜底，记录 `finish_reason`，补齐空响应回归测试和元信息/语言标签处理。
2. 守恒管线：引入结构化载荷、稳定源段、批量 ID 协议、两层验证、确定性组装和审计元数据，并让 optimize 默认走新管线。

旧的重叠输出合并、模糊邻接去重和单纯长度兜底不得作为新管线的正确性基础。它们可在迁移完成后删除；迁移期间也不得成为新管线失败时的降级路径，失败只能回退原文。

## 12. 完成标准

只有同时满足以下条件才可宣称修复完成：

- 所有新增和既有相关测试通过。
- 空响应复现用例不再丢失任何源段。
- 真实任务 `2f0c1c44` 的开场和所有源段完整保留。
- 日志和审计能定位每一次回退。
- LLM/API 完全不可用时仍能输出完整原文稿。
- 未验证的 LLM 输出不存在进入最终稿的代码路径。
