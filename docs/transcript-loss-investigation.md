# 转录内容丢失问题调查报告

> **调查日期**：2026-07-22
> **调查对象**：AI-Video-Transcriber_RE 项目，3.8 小时长访谈转录丢内容问题
> **状态**：根因已定位，方案待评审。本文档供独立审阅。
> **关键结论**：问题**不在 ASR 转录阶段**，而在 **LLM 文本优化（optimize）阶段**。原始 ASR 输出完整正确，但经 DeepSeek 优化后丢失约 **39% 内容**，其中包括主持人开场白。

---

## 1. 摘要（TL;DR）

| 项目 | 结论 |
|---|---|
| 用户报告 | 3 小时长视频转录稿"从第一段开始文字就不对，跳过了开头，直接进入中段" |
| 是否 ASR 问题 | **否**。原始 ASR 输出 80,041 字符，完整且正确，开头是主持人开场白 |
| 实际丢内容位置 | **optimize（DeepSeek 文本优化）阶段** |
| 丢失量 | 优化后剩 48,799 字符（60.97%），**丢失约 39%**；其中开头前 3,895 字符（主持人开场 + 嘉宾介绍）完全消失 |
| 根本原因 | ASR 输出**零标点**（0 个句号/问号/感叹号/逗号）→ 分块器的句子切分完全失效 → 8 万字被识别为**单个"句子"** → 退化为每 4000 字符一刀的**机械硬切** → DeepSeek 收到头尾残缺的碎片 → 默认补偿行为是丢弃残缺边缘 + 压缩能理解部分 → 系统性丢内容 |
| 兜底为何失效 | 所有兜底机制都用"字符长度"作代理指标；DeepSeek 丢开头 + 改写其余，长度仍达标，逃过检测。整体兜底阈值 60%，本次恰好 60.97%，差约 774 字符未触发 |
| 推荐方案 | **重叠切块**（3000 字符/块，相邻重叠 500 字符）+ 精确字符串匹配去重 + n-gram 覆盖率兜底。不增加 LLM 调用轮次 |

## 5. 根因分析

### 5.1 排除项：不是 ASR 的问题

| 验证点 | 结果 |
|---|---|
| ASR 是否跳过开头 | **否**。原始 ASR 输出从主持人开场白"hello 大家好我是小俊…"开始，完整到片尾"这里是商业访谈录…公众号是 语言及世界" |
| ASR 是否丢内容 | **否**。80,041 字符完整，内容连贯正确 |
| 速度优化是否牺牲质量 | **否**。SenseVoice 是非自回归模型，111x 实时是其正常能力，转录结果正确 |
| `woitn` 语言乱码 | SenseVoice 首个 chunk 产出的垃圾语言标签（`transcriber.py:249` 的 `_parse_language` 原样返回未知标签）。属独立 bug，导致纯中文稿被当 `woitn→zh` 翻译，但不影响 optimize 内容丢失 |

### 5.2 定位：optimize 阶段

证据链：
1. 原始 ASR（`raw_*.md`）完整 → 丢失发生在 ASR 之后。
2. 优化稿（`transcript_*.md`）丢失 39% + 跳过开头 → 丢失发生在 optimize。
3. translate/summarize 的输入是已优化的 `script`（`main.py:254, 276`）→ 它们的丢失是"继承"自 optimize，非独立原因。

### 5.3 第一性原理：为什么会丢

optimize 阶段流程（`summarizer.py:367` `_format_long_transcript_in_chunks`）：

```
原始文本 → 按[。！？]切句子 → 组装≤4000字符块 → 逐块送DeepSeek优化
         → _strip_context_echo(相似度去重) → 70%块级长度兜底
         → 邻接去重 → 60%整体长度兜底 → 段落≤400字符强制切分
```

**四个层次的根因**：

**① 分块畸形（根因，确证）**
ASR 输出零标点 → 句子切分失效 → 机械硬切 → 每块的边界落在句子/词语中间。DeepSeek 收到的是**头尾残缺的文本碎片**。

**② DeepSeek 对残缺碎片的补偿行为（机制，部分推断）**
DeepSeek 处理残缺文本时，默认行为是丢弃无法理解的边缘 + 压缩/改写能理解的中间部分。尤其倾向把主持人开场白、寒暄判断为"非正文冗余"删除（代码注释 `summarizer.py:407-409` 已承认此已知失败模式）。
> ⚠️ **推断部分**：块级 LLM 输出未落日志，"块 1 丢了开场白但长度仍达标逃过兜底"是基于长度数据与最终结果的推断，无块级直接证据。

**③ 兜底机制用"长度"作代理，无法检测"局部丢失+局部膨胀"（确证）**
- 70% 块级兜底（`summarizer.py:424`）：只比较优化前后字符数。DeepSeek 丢开头 + 改写其余，长度仍 ≥ 70% → 逃过检测。
- 60% 整体兜底（`summarizer.py:315`）：本次 60.97%，仅高出阈值 0.97 个百分点（余量 774 字符）→ 逃过检测。
- 根本缺陷：**字符长度 ≠ 内容保真度**。

**④ 输出 token 上限可能偏紧（待验证）**
`_format_single_chunk` 的 `max_tokens=4000`（`summarizer.py:198`），而输入块达 4000 中文字符。若 DeepSeek 中文分词比例使 4000 tokens 不足以覆盖 4000 中文字符的完整输出，会导致被动截断。**此项未实测验证，列为待查。**

## 6. 解决方案

### 6.1 设计原则（用户决策）

用户明确要求**保留 DeepSeek 介入**——ASR 输出零标点、含错别字与人名错误，需要 LLM 修正。因此方案目标是"保留 DeepSeek，但消除丢内容"，而非去掉 DeepSeek。

### 6.2 核心方案：重叠切块（Overlap Chunking）

**思路**：与其事后修复"硬切的伤口"，不如不让伤口出现。在切块时引入重叠窗口，使每个硬切边界都被完整句子覆盖，DeepSeek 始终拿到可理解的完整文本。

```
现状（硬切，无重叠）：
块1: [0:4000]    ...那接下来就是我对克里伊鸣的访|←硬切→|谈 期待二零二六年...   ← 边缘残缺
块2: [4000:8000] 谈 期待二零二六年 我们和AI共同进步 确实我们不做人形...         ← 边缘残缺

方案（重叠 500 字符）：
块1: [0:3000]     ...那接下来就是我对克里伊鸣的访谈 期待二零二六年 我们和AI共同进步
块2: [2500:5500]  ...我们和AI共同进步 确实我们不做人形因为他们要说做人性我就不来了...
                 ↑ 重叠区 [2500:3000] = 完整句子覆盖了原硬切边界
```

### 6.3 具体改动

| 改动 | 位置 | 内容 |
|---|---|---|
| **重叠切块** | `summarizer.py:385-403` 分块逻辑 | 每块 3000 字符，相邻块重叠 500 字符。`start[i+1] = start[i] + 2500` |
| **精确去重** | `summarizer.py:432-444` 邻接去重 | 用重叠区的精确字符串匹配（`str.find`）定位拼接点，替代当前的模糊 `_find_overlap_between_texts`。确定性去重，不误删 |
| **n-gram 覆盖率兜底** | `summarizer.py:424-426` 块级兜底 | 从"字符长度 < 70%"改为"原文 4-gram 在输出中的覆盖率 < 85%"。检测内容保真而非长度 |
| **整体覆盖率兜底** | `summarizer.py:306` `_maybe_overall_fallback` | 从"长度 < 60%"改为"全文 4-gram 覆盖率 < 90%" |
| **max_tokens 放大** | `summarizer.py:198` | 4000 → 8000，消除被动截断风险（待确认是否必要） |

### 6.4 Before / After 对比

| | 现状（Before） | 方案（After） |
|---|---|---|
| 切块方式 | 硬切 4000 字，无重叠 | 重叠切 3000 字，重叠 500 字 |
| 块数（8 万字） | ~21 块 | ~32 块 |
| LLM 接收内容 | 头尾残缺碎片 | 每块含完整句子的文本 |
| DeepSeek 行为 | 看不懂碎片 → 丢弃/压缩 | 能看懂 → 按语义修正 |
| 去重方式 | 模糊去重（可能漏/误删） | 重叠区精确匹配（确定性） |
| 块级兜底指标 | 字符长度 < 70% | 4-gram 覆盖率 < 85% |
| LLM 调用轮次 | 1 轮 | **1 轮（不变）** |
| 预计耗时 | ~20 分钟 | ~30 分钟 |
| 额外 token | — | +17%（重叠区被处理两次） |
| 预期结果 | 丢 39%，开头全丢 | 完整保留 |

### 6.5 备选 / 降级方案（若主方案效果仍不达标）

1. **缩小块到 1500-2000 字符**：进一步降低单块丢失绝对量，但增加调用次数。
2. **分块前先加标点**：先用一次轻量 DeepSeek 调用给无标点文本加句号（仅加标点，不优化），再自然切块。代价是 LLM 调用轮次翻倍（21→42 块 + 1 次加标点），耗时 ~40 分钟。
3. **OPTIMIZE_ENABLED 开关**：允许整体跳过 DeepSeek 优化，直接用规则分段（`_apply_basic_formatting`）。一字不丢但无错字修正。作为终极保险。

### 8.4 实施复核补充（2026-07-22）

后续结合真实产物与旧实现复核，确认了直接丢失机制：部分 LLM 分块返回空字符串，而旧代码的块级保护写成 `if oc.strip() and ...`。空结果会令条件为假，既不触发长度兜底，也不会在合并时补回原块，因此对应正文被静默跳过。整体保护同样要求合并结果非空，存在相同的 fail-open 缺口。

机械硬切、零标点和有限输出窗口会提高 LLM 返回异常结果的概率，是重要的可靠性诱因；但它们不是本次已经证实的直接删除动作。因此，本文第 6 节的“重叠切块 + 去重 + n-gram”方案不再作为最终正确性基础：它只能降低异常概率，不能证明每个源区间都有最终去向。

最终采用的实现以原始正文为不可变事实源：确定性划分带稳定 ID 的小段，LLM 只提交逐 ID 的修改建议，程序逐段检查结构与内容守恒，并严格按原 ID 顺序组装。任何空响应、漏 ID、重复 ID、截断、解析失败或过度改写都只会使相应段回退原文；原始转录保存失败则停止后续处理。同时补充不含正文的审计 sidecar，用哈希、偏移、状态和编辑统计解释每段为何采用优化结果或原文。
